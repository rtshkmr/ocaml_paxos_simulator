** First time setup
For folks who are trying OCaml for the first time, there's 3 steps to take:

1. Run =make setup=

   This *setup script is for convenience* and follows the instructions [[https://ocaml.org/install#linux_mac_bsd][from the official docs]]:
   * It installs [[https://opam.ocaml.org/][opam]] (the package manager)
   * It creates a local OCaml switch in =paxos/_opam=
   * It installs ocaml and dune using opam
   * It installs all dependencies that have been locked for this project

2. Update your =PATH= variable and reload your shell.

   Follow the instructions that =make setup= provides at the end of its run. Some common sources of error:

   * Remember to reload the shell (either by restarting your terminal or sourcing your config file e.g. =source ~/.zshrc=).

   * You'll need to be able to access =opam= and =dune= from your shell, updating the =PATH= variable will allow you to do so. If you call =which opam=, it should point you to when =opam= has been placed.

   * Remember to set your =opam switch= to the local switch. Calling =which dune= and =which ocaml= should be showing locations within the local opam switch.

3. Run =make magic=!
   It will:
   - check =opam= / =dune= are accessible
   - activates local opam switch
   - builds the project incrementally
   - runs simulators with the flags you supply it






This will spawn the simulator. If you need help, just type =/help= into the repl-like interface after the prompt (=>>>=).

* Motivation

This project is a *minimal, literate implementation* of the [[https://en.wikipedia.org/wiki/Paxos_(computer_science)][*Paxos consensus algorithm*]] written in OCaml.

From a learning perspective, this project is *both*:

 1. a *learning exercise* in applying OCaml’s language primitives into a classic, distributed algorithm and,


 2. an *attempt to be able to showcase* of what the language enables when you design for correctness and composability from the ground up.

The idea is simple: instead of reading yet another paper about distributed consensus, I wanted to see how it behaves — how proposers, acceptors, and learners coordinate to agree on a single value even when messages fail or nodes “go bad.”

Inspired by TigerBeetle’s interactive consensus demos ([[https://www.youtube.com/watch?v=w3WYdYyjek4&t=3185s][their product demos are so cool]] [[[https://tigerbeetle.com/blog/2023-07-11-we-put-a-distributed-database-in-the-browser/][blog]]]), this project focuses on clarity, correctness, and communication, not fancy graphics or production engineering. The simulation runs deterministically, with traceable message logs showing how Paxos resolves contention and failure.

** Why this topic?

My foray into the distributed computing world was thanks to a friend introducing me to the Elixir world a while ago. One of the reasons the devex within the Elixir ecosystem is a wonderful experience is that our systems can resolve most of the classic robustness problems in distributed systems by relying on patterns built on [[https://www.erlang.org/doc/system/design_principles.html][OTP Design Principles]] (using powerful units like GenServers, Supervision Trees). The idioms within the Elixir ecosystem are easy to use, and there's definitely a lot of intuition to gain from understanding the knowledge beyond the abstraction barriers.

Now that I'm learning OCaml, it's a good chance for me to explore the expressiveness that the OCaml language and appreciate the classic consensus problems.

I definitely can forsee some scope creep happening.

** Implementation Plan (draft)
1. **Bridge Paxos knowledge** — review Lamport’s “Paxos Made Simple” and Tom Cocagne’s examples
2. **Understand the reference Python repo** — follow message flow, list all message types and states
3. **Design OCaml modules** — define signatures for Proposer, Acceptor, Learner, and Network
4. **Review OCaml module / dune basics** — small refresher on how to structure a library with submodules
5. **Implement v0 (core algorithm)** — deterministic single-threaded simulation
6. **Iterate and test scenarios** — add fault injection, logging, and a few “step-through” examples
7. **Write-up** — produce blog-style README + literate trace
