Paxos Strategy Naming — PaxosPolicy

Name	Connotation	When to Use

****** Conceptual Model

Key moving parts and how they relate to one another

******* A: Ownership and Control Flow

Here's what happens at runtime (for the simulation).

1. Simulation Runtime (Event Loop)
   - owns the main ticking / stepping logic
   - drives the overall simulation:

     - generating timed events (e.g. node x initiates proposal), faults and stimuli

     - Calls into =EventBus.publish= to simulate the network transmission

2. Event Bus
   - a pure registry & routing layer
   - holds subscriptions =(topic, callback)=
   - doesn't manage time or scheduling and is purely REACTIVE

3. Nodes
   - they react to incoming messages via callbacks
   - may generate outgoing messages by publishing to the bus
   - they should be able to handle the bulk of the message flow autonomously
   - the simulation loop could occasionally, as part of its stimuli-creation be able to nudge a node to make a proposal.

******* B: Disambiguating Messages and Events

| layer   | concept                         | example                                                  |
| --      |                                 |                                                          |
| message | paxos protocol-level unit       | PermissionRequest, Suggestion...                         |
| event   | Simulation/meta-level occurence | "Node 1 published message X at time T", "Fault injected" |

  * *messages* are what nodes send, *events* are what simulation records

    =Event= may wrap message or meta-actions

    an example:
    #+begin_src ocaml -n
type 'v event =
  | MsgDelivered of { from: node_id; to_: node_id; msg: 'v Message.t; timestamp: Time.t }
  | FaultInjected of { node: node_id; fault: string; timestamp: Time.t }
  | SimulationTick of int

    #+end_src
  * following,
    - =EventBus=: routes messages between NODES -- so this is an active registry

    - =EventLog= kind of thing: collects events for introspection, debugging, visualisation
******* C: Delivery Semantics

The end-goal is to use async delivery mechanisms in an ordered format.

_For v0: more like a functional graph_
 - we will use a sync publish -- so directly invoking callback
 - we make things deterministic to be easy

_For v1: more of a timed-actor simulation_
 - dispatch queue per subscriber (=node_id=) which will be serviced by the simulation loop

 - we can model network latency or dropped packets here

 - even better would be to directly use the socket instead of spending effort with all this simulation plumbing
******* D: Type Uniformity

All topics should just carry the same ='v Message.t= because it will be easier to implement and we can use a single event-bus for the whole simulation

If we need heterogeneous payloads (e.g. meta-events, logs...) then we can wrap ='v Message.t= in a polymorphic variant or GDT @ the event layer (just for simulations)

******* E: Simulation Runtime -- "Pseudoconcurrent" simulation

It's "Pseudoconcurrent" because we can pause, inspect, step and replay

Needs to support the 2 key features:
1. ability to inspect:
   - the state of the bus
   - the state of ALL the nodes

2. Should be deterministic in its stepping / tick driving
