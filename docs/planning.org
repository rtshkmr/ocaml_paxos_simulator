**** General Patterns Observed from Implementation Approach
1. separation of concerns via mixins

   the code uses mixins to separate functionality, this will work well with our ocaml demo.
   there are functional and imperative parallels in ocaml that we can use for this.

   a) master lease implementation has a cli flag for it on whether to include or not (since it's an optimisation)

2. multi-paxos chain config within config.py:
   - peers and their sockets
   - location of persistent state-files -- just file-io-ed

     the state file is to support recovery

3. on the networking mesh side, they're just using UDP fire-and-forget packets for the message passing.

4. client code

   - that's what the *client code* is for: seems like just a way to trigger the proposal initiation (and pick a server (i.e. peer node) as the initiator)

     this client code intentionally omits a lot of error-handling which is good because the server logic should be the one handling it.

   - idea: this part of the code seems to be essentially all the demo-orchestration stuff as well.

***** Messenger
- handles all the message passing strategy
- the code has message-type specific functions which is name-resolved via dynamic lookup
- comms is via UDP, simple JSON encoding format

***** BaseReplicatedValue
- represents the replicated value
- has some file-io persistence
- is a passive class:

  - converts message into a call to the underlying PaxosInstance, potentially sends a reply?

  - Does NOT:
    - initiate sending of original msgs
    - doesn't drive resolution forward

- 3 goals:
  a) on resolution, creates PaxosInstance object

  b) Bridges Messenger Class (network access) and PaxosInstance object

  c) does the persistent storage within a file prior to each Promise and Accept Message (and also upon resolution)
***** ComposablePaxos

Defines core paxos algo, set of composable classes

Classes agnostic of:
1. message passing functionality within the network layer
   - the classes do have reception handlers though

***** Resolution Strategy

Mixin class with logic for:
1. forward progress towards resolution
2. anti inter-peer interference is handled here

* Intentional Shortcuts
Since I'm keeping this to a 2 day effort, there's a need to be aware of some time-sinks that I will most likely side-step first.

The design of my interfaces should be sufficient to add some of these areas incrementally with minimal lift.

A. Codebase Organisation will be low-priority:

   Getting lost in OCaml’s module system is something I can't afford. I shall keep everything flat until it works. I can modularise later.

B. Visualisation trap:

   We shall do barebones visualisation (some basic log dump).

   We shall NOT do browser-based visualisations or JSON timelines until the v0 part works end to end.

C. Async trap:

   Lwt/Async is cool, but adds a large learning curve — it will burn our schedule. We will simulate concurrency deterministically first.

D. Testing complexity:

   We will resist property testing or QuickCheck; we will just write hand-driven deterministic cases.
